# Критерії прийняття

Зафіксовано 2026-09-27, до першого рядка коду. Пороги змінюються лише через розділ «Поправки» з причиною. Результати звітуються чесно, включно з непройденими критеріями.

## Набори питань

- **Робочий (dev)** — `evals/dev.jsonl`.
  - ~60 питань і ~6 діалогів. Їх згенерував окремий агент за таксономією (`evals/taxonomy.md`) і схемою розмітки (`evals/label_schema.md`).
  - Плюс 3 публічні приклади з умови. Вони не входять у метрики узагальнення.
  - Використовується вільно під час розробки.
- **Прихований (held-out).**
  - ~40 питань і ~4 діалоги. Їх написав окремий агент лише за текстом умови: без таксономії, без доступу до репозиторію.
  - Зберігається поза репозиторієм; тут фіксується лише SHA-256 (`evals/heldout.sha256`).
  - Запускається не більше двох разів: після стабілізації і фінально. Під час розробки видно лише агреговані результати.
  - Після фінального прогону публікується в `evals/`.
- **Базова лінія** — Claude Haiku 4.5 без навички на 15 питаннях робочого набору.

## A. Структура (усе обов'язкове)

| # | Критерій | Як перевіряємо |
|---|---|---|
| A1 | SKILL.md відповідає специфікації Agent Skills | `skills-ref validate` або тест, що відтворює правила специфікації |
| A2 | SKILL.md ≤ 500 рядків і ≤ 5000 токенів | тест (токени оцінюються як символи / 4) |
| A3 | усі власні матеріали — в директорії навички; без бінарників; залежності декларовані (PEP 723) із lock-файлом | тест + запуск `--help` з чистого клону |
| A4 | приватний email відсутній у файлах і в усій історії git | перевірка перед кожним комітом (хук) і фінальний пошук по історії |

## B. Коректність коду (усе обов'язкове)

| # | Критерій |
|---|---|
| B1 | модульні тести проходять офлайн |
| B2 | Синтетичні ряди з відомим р/р від −40% до +60%, сезонністю, шумом і сплесками: медіанна похибка р/р ≤ 3 п.п., покриття 95%-інтервалу ≥ 80%. Уведений сплеск виявляється, а р/р без сплесків відрізняється від істини не більше ніж на 5 п.п. |
| B3 | Для ≥ 5 реальних статей місячні суми з наших щоденних даних (з заповненням нулями) точно збігаються з місячними значеннями API |
| B4 | Усі відкриті мовні розділи з sitematrix резолвляться за кодом; коди-винятки (`yue`, `gsw`, `be-tarask`, `nan`, `lzh`) резолвляться правильно |
| B5 | Кожен PDF, створений у evals, має рівно 1 сторінку; з нього витягується текст з кирилицею і діакритикою |
| B6 | Метаморфні інваріанти коду: порядок мов не змінює результатів; додавання мови не змінює метрик інших рядів; множення ряду на константу не змінює відносних метрик |

## C. Поведінка агента на Claude Haiku 4.5

Умови прогону: Claude Code headless, ізольоване оточення (`--setting-sources project`), навичка встановлена в тимчасовий проєкт.

**Універсальні перевірки** — однакові для кожного прогону, незалежно від питання:

| # | Перевірка |
|---|---|
| U1 | навичку використано (команди `scripts/wiki.py`) |
| U2 | агент не писав власного коду для отримання чи обробки даних |
| U3 | числа у відповіді є у виводі інструментів (автоматично; сумнівні випадки перевіряє суддя) |
| U4 | названо вікно даних і рівень довіри (якщо був аналіз) |
| U5 | є припущення або обмеження |
| U6 | немає тверджень про готовність платити чи про країни без застереження |
| U7 | запитані артефакти валідні (PDF — рівно 1 сторінка) |
| U8 | мова відповіді збігається з мовою користувача |

**Успіх задачі** оцінює LLM-суддя за рубрикою з цитатами-доказами. Задача успішна, якщо:
- відповідь відповідає на питання;
- виконано очікувані поведінки з розмітки;
- жодної забороненої поведінки.

| # | Критерій | Поріг |
|---|---|---|
| C1 | Вигадані числа, підтверджені суддею, на прихованому наборі | **0** |
| C2 | Прогони прихованого набору, що пройшли всі універсальні перевірки | ≥ 90%, нижня межа інтервалу Вілсона ≥ 80% |
| C3 | Успіх задачі на прихованому наборі | ≥ 80% |
| C4 | Розрив «робочий − прихований» за успіхом задачі | ≤ 10 п.п. |
| C5 | Стабільність: два прогони на питання в прихованому наборі дають однаковий висновок | ≥ 85% |
| C6 | Питання «частково» / «поза межами» (обидва набори): правильна реакція | ≥ 90% |
| C7 | З навичкою проти базової лінії (успіх задачі) | +30 п.п. і більше |
| C8 | Ефективність на одноходових питаннях | медіана ≤ 10 викликів інструментів і ≤ 3 хв |
| C9 | Повторні запити в діалогах: незмінені ряди не завантажуються повторно | за логом кешу |

Зрізи за таксономією (намір, письмо, пастки) — діагностика, а не пороги: на зрізі з 10 питань інтервал становить ±19 п.п.

## Поправки

1. **2026-09-27, після ітерації 3.** Робочий набір прогнано 3 рази (по одному прогону на питання, без повторів), не «до стабілізації без обмеження кількості». Причина: при n=71 і одному прогоні на питання зміни між ітераціями (24% → 23% → 21% успіху задачі) статистично невиразні (інтервали Вілсона повністю перетинаються) — кожна наступна ітерація ризикувала або ганятися за шумом, або підганяти рішення під конкретні провали dev.jsonl, що прямо суперечить вимозі замовника. Зупинились після того, як усі знайдені дефекти були підтверджені логами (а не лише незгодою судді) і виправлені: крах вердикту на порожньому діапазоні, і головний — 27% прогонів із вигаданим числом через формат виводу сезонного профілю (індекс замість готового відсотка). Робочий набір і далі можна прогнати ще раз (evals/run_evals.py --set dev), але це не входить у поточну оцінку.
2. **2026-09-27, стабільність (C5).** Двократний прогін «до стабілізації» (`heldout-1`) і фінальний (`heldout-2`) виконано на прихованому наборі, як і планувалось — там же й рахується C5. Кожна ітерація робочого набору мала лише 1 прогін на питання (не 2+), тож стабільність на робочому наборі не вимірювалась; це свідомий компроміс бюджету сесії, а не відхилення від наміру.
